# ARTEMS CARBON — интеграция Т-Банк EACQ и статистика продаж

Состояние: **план / платежи не подключены**. До ввода реальных продаж согласовать юридически правила передачи автомобиля и связь количества покупок с шансами.

## Архитектура

- GitHub Pages: публичная витрина и UI корзины. Не размещать TerminalKey Password или подпись в JS.
- Отдельный HTTPS API на VDS/Selectel (Node.js), PostgreSQL для заказов и платежей.
- На странице размещена публичная шкала продаж, конфигурация API через `<meta name="artems-api-base" content="">`. Пока значение пустое, отображается «— / 9 500» и честное пояснение.
- Публичный эндпоинт: `GET /api/public/stats` -> `{"soldLessons":1234}`. Значение целое, только подтверждённые и невозвращённые единицы видеоуроков, без персональных данных.
- На API нужны CORS только с домена витрины, ограничение запросов и кэширование коротким TTL (например, 30–60 секунд).
- Админка требует настоящую серверную авторизацию; текущий пароль в браузере не защита.

## Схема оплаты

1. Покупатель вводит контактные данные, количество, подтверждает условия.
2. `POST /api/orders`: сервер проверяет состав заказа, остаток (для видеоуроков максимум 9500, если юридически согласовано), цены из БД; создает `pending` заказ с уникальным `OrderId`.
3. Сервер подписывает `/v2/Init` по инструкции Т-Банка. Передаёт `TerminalKey`, `Amount` в копейках, `OrderId`, `Token`, `PayType: "O"` (при соответствии настройке терминала), `NotificationURL`, `SuccessURL`, `FailURL`, `Receipt` при включённой фискализации.
4. Возвращает клиенту только платежный URL, полученный от банка. Клиент переходит на `PaymentURL`.
5. `POST /api/payments/tbank/notification`: сервер проверяет подпись Token (все простые поля уведомления согласно документации банка), `TerminalKey`, `PaymentId`, `OrderId`, сумму, статус и целостность данных; обеспечивает идемпотентность `(PaymentId,Status)`.
6. Только `CONFIRMED` считается успешной продажей; `AUTHORIZED` не учитывается. Считать единицы оплаченного заказа в одной транзакции с изменением статуса, исключая двойное начисление.
7. Возвраты/отмены учитываются отдельно; отчётность и счётчик корректируются.
8. При сомнении сверять статус через `/v2/GetState`, не доверять браузерному SuccessURL.
9. Уведомление банка должно получать `200 OK` с телом `OK` после безопасной обработки; нужен журнал и повторная обработка.
10. Email доступ к реальному уроку и другие разрешённые бонусы выдаются только после CONFIRMED.

## Сущности

- `customers(id,email,created_at)`
- `orders(id,customer_id,total_kopecks,status,created_at,paid_at)`
- `order_items(order_id,sku,quantity,unit_price_kopecks)`
- `payments(id,order_id,provider_payment_id,amount_kopecks,status,created_at)`
- `payment_events(provider_payment_id,status,event_hash,processed_at)`
- `refunds(payment_id,amount_kopecks,refunded_at)`
- `course_access(customer_id,order_item_id,grant_at)`

При необходимости — резервирование остатков и отдельное учётное правило для 9500 единиц, чтобы не продать больше лимита при одновременной оплате.

## Что считать

- `soldLessons` = сумма qty строк sku=video_lesson из оплаченных заказов (CONFIRMED), скорректированная на возвраты.
- `uniquePaidCustomers` = distinct customer_id с оплаченными заказами.
- `paidOrders` = количество оплаченных заказов.
- `grossRevenueKopecks`, `refundsKopecks`, `netRevenueKopecks`.
- Продажи продукции **не включать** в шкалу 9500 уроков.

## Проверки перед запуском

- Тестовый терминал DEMO (см. тест-кейсы Т-Банка).
- Успешная оплата; отказ; отмена; возврат; частичный возврат.
- Повторная нотификация и уведомления не по порядку.
- Подмена суммы клиентом; чужой `OrderId`; неверный Token.
- Перезагрузка SuccessURL без повторного начисления.
- Конкурентные покупки при достижении лимита 9500.
- Отказ сети/временная недоступность API: публичный счётчик отображает «—» без вымышленных продаж.
- Тестовая/реальная фискализация и доставка чеков.
- Серверная авторизация админки, секреты вне Git, аудит действий.
