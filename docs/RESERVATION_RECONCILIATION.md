# PR #76 — сверка зависших резервов с Т-Банком

**Статус: тестовый этап; вручную запускаемый одноразовый worker, никаких cron и изменений VDS.**
Этот PR основан на **PR #75** (`feat/lesson-number-reservation-before-payment`); сливать только после проверки зависимостей и прохождения CI.

## Задача

Старая бронь `lesson_number_pool.reserved_order_id` не освобождается по таймеру. Время `reservation_expires_at` (30 минут) — лишь **порог, после которого можно запросить статус у банка**, а не доказательство отказа покупателя.

T-Банк предоставляет `POST /v2/GetState`: https://developer.tbank.ru/eacq/api/get-state

Согласно банковскому сценарию существуют как промежуточные, так и окончательные статусы. В целях безопасности текущий reconciliation-worker разрешает освобождение **только для `CANCELED` и `REJECTED`** при `Success:true`. Даже при `DEADLINE_EXPIRED`, `AUTH_FAIL`, `NEW`, `FORM_SHOWED`, `AUTHORIZED`, `CONFIRMED`, сетевой ошибке или неизвестном статусе **ничего не освобождать** до отдельной оценки.

## Порядок выполнения

1. Worker ищет `pending`-заказы с неотпущенной просроченной бронью и заполненным `provider_payment_id`. Заказы с неопределённым результатом /Init и отсутствующим `PaymentId` остаются зарезервированными: их нельзя безопасно освобождать без ручной сверки.
2. Отправляет **подписанный Token** запрос GetState с существующим `PaymentId`; не меняет состояние банка.
3. Перед освобождением сверяет `PaymentId`, `OrderId`, `TerminalKey`, `Amount` и `Success`. Любое расхождение означает отказ от операции.
4. Для финальных `CANCELED` или `REJECTED` в одной PostgreSQL-транзакции: блокировка заказа `FOR UPDATE`, общий advisory lock `(9500, 2026)`, сверка количества забронированных номеров, очистка брони, перевод заказа в `cancelled`, запись в таблицу `lesson_reservation_release_audit`.
5. Если заказ уже стал `paid` или `cancelled`, worker не меняет его. Повторный запуск идемпотентен.
6. При пришедшем позже `CONFIRMED` к уже отменённому заказу webhook выдаёт отдельную критическую ошибку для ручной сверки, **не выдаёт повторно номера**.

## Настройки и запуск

- Миграции: сначала `server/sql/006_pre_payment_reservations.sql`, затем `server/sql/007_reservation_reconciliation.sql`.
- Используются уже предусмотренные переменные `DATABASE_URL`, `TBANK_TERMINAL_KEY`, `TBANK_PASSWORD`, `TBANK_API_URL`. Новая защита — `RECONCILIATION_ENABLED=true` **только для отдельного процесса** и только после настройки тестового стенда и БД.
- Команда для изолированной тестовой среды: `npm run reservations:reconcile`.
- Без `RECONCILIATION_ENABLED=true` команда завершается отказом. **Не добавлять эту переменную в production `.env` до полного тестирования и проверки правовой части.**
- Текущий PR **не добавляет systemd timer**, не вызывает /Cancel, не активирует боевые платежи и не запускает миграции автоматически.
- Рекомендуемый дальнейший шаг: добавить controlled scheduled job после подтверждения тестами, алертинг зависших броней, сверку оплаченных заказов и бухгалтерскую reconciliation процедуру.

## Интеграционные проверки (изолированная БД + имитация банка)

- Несколько одновременных заказов не пересекаются по номерам.
- При исчерпании номеров оплата не инициируется.
- `NEW` после истечения таймера не освобождает бронь.
- `CANCELED` с несовпадающей суммой не освобождает бронь.
- `CANCELED` с корректными идентификаторами освобождает ровно свою бронь и записывает аудит.
- Повторный запуск не приводит к повторному освобождению.
- Рефанд оплаченного заказа не возвращает номера в доступный пул.

## Ограничения перед реальными продажами

- Даже окончательный статус банка требует оценки гарантии невозможности последующей оплаты; для сомнительных случаев сохранить бронь и разбирать вручную.
- Не обработаны массовые заказы без `PaymentId`, сетевые разрывы после /Init и частичные возвраты. Отдельная задача — запрос статуса по OrderId/договор с банком и управляемое закрытие платежа.
- Рабочая подписанная банка /GetState в реальном тестовом терминале **не проверена**; использован только mock-банк в CI.
- Нет независимого подтверждения юридической, фискальной и банковской готовности, поэтому **PAYMENTS_ENABLED остаётся выключен**.
