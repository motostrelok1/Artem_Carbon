# Artem Carbon — план защиты от DDoS и HTTP-флуда

**Статус:** план, без применения к production. **Ответственный этап:** отдельный implementation PR с тестами и контролируемым rollout. Дата: 2026-11-22.

## Цель и границы

Защитить `artemcarbon.ru`, `www.artemcarbon.ru` и `api.artemcarbon.ru` от HTTP-флуда, перебора паролей, медленных соединений и перегрузки Node.js/PostgreSQL, сохранив регистрацию покупателя, создание заказов, отправку запросов на оплату, webhook Т-Банка, вход администратора и GitHub Actions. **Nginx сам по себе не защищает канал VDS от объёмных L3/L4 DDoS**: для этого требуется upstream-фильтрация провайдера или внешняя DDoS-защита.

### Подтверждённое текущее устройство (из репозитория)

- `scripts/deploy-full-vds.sh` при каждом релизе **перезаписывает** `/etc/nginx/sites-available/artemcarbon.ru`; все постоянные изменения Nginx нужно закреплять именно в deploy-скрипте или в контролируемых им include-файлах.
- Nginx обслуживает статический сайт и проксирует `/api/` на `127.0.0.1:3002` на двух HTTPS-хостах; `/health` также проксируется в Node.js. HTTP перенаправляется на HTTPS, кроме ACME challenge.
- Certbot использует сертификат `/etc/letsencrypt/live/artemcarbon.ru` для трёх имён. Не ломать renew и `/.well-known/acme-challenge/`.
- Т-Банк вызывает `POST /api/payments/tbank/notification`; приложением проверяется подписанный Token, идентификатор платежа и сумма. Клиентские покупки: `POST /api/orders`; админка: `/api/admin/*`; публичный счётчик: `GET /api/public/stats`.
- `server/src/app.js` использует PostgreSQL pool max 10 и локальный rate limiting login в памяти процесса. На входе Nginx есть смысл поставить отдельные лимиты, не полагаясь только на приложение.
- GitHub Actions развёртывает сайт по SSH отдельным пользователем; менять firewall/SSH без сохранения рабочего доступа нельзя.

## Этап 1 — Nginx anti-flood (отдельный implementation PR)

### Базовые стартовые параметры для проверки под нагрузкой

| Область | Предложение | Комментарий |
|---|---|---|
| Обычный `/api/` | `8r/s` на исходный клиентский IP, `burst=20` | Сглаживание/очередь, **без** `nodelay` на старте; смотреть реальные 429/latency |
| `POST /api/admin/login` | `5r/m`, небольшой `burst` | Строже общих API, не применять только общий лимит |
| Одновременные соединения с API | `limit_conn 20` на IP | В HTTP/2 запросы/стримы могут учитываться как соединения |
| Ответ при превышении | HTTP `429` | Явный код и мониторинг, чтобы не путать с 5xx |
| Заголовки/тело/отправка | 10/15/15 секунд | Проверить поведение на медленных мобильных сетях |
| Idle keepalive | 20 секунд | Не отключать HTTP/2 и TLS |
| JSON-тело для API | Предварительно 128 КБ | Приложение ограничивает JSON до 64 КБ; не применять к загрузке фото/статике сайта |
| Публичная статика | CDN/кеш | Не лимитировать фотографии по правилам для API |

Пример **лишь для разработки**, не вставлять целиком в production без анализа контекстов:

```nginx
# http context: /etc/nginx/conf.d/*.conf, если этот include находится внутри http {}
limit_req_zone $binary_remote_addr zone=ac_api:10m rate=8r/s;
limit_req_zone $binary_remote_addr zone=ac_login:10m rate=5r/m;
limit_conn_zone $binary_remote_addr zone=ac_connections:10m;
limit_req_status 429;
limit_conn_status 429;
client_header_timeout 10s;
client_body_timeout 15s;
send_timeout 15s;
keepalive_timeout 20s;
```

В двух HTTPS vhost добавить ограничения **в существующие location**, сохранив `proxy_pass`, заголовки и таймауты; `limit_req zone=ac_api burst=20;`, `limit_conn ac_connections 20;`, `client_max_body_size 128k;` — примеры. Создать **отдельный `location = /api/admin/login`** с собственной более строгой зоной, повторив настройки проксирования. Проверить порядок location и то, что точный location не обходит необходимые общие ограничения случайно.

**Отдельно разобрать маршруты:**
- `POST /api/orders`: защищать от спама и дорогого `Init`, но без блокировки нормальных покупателей за одним NAT; добавить серверный per-user / per-order rate limit и идемпотентность создания заказа отдельным решением.
- `POST /api/payments/tbank/notification`: не ставить агрессивный IP-лимит, который может мешать подписанным уведомлениям и повторным доставкам банка. Сохранять проверку подписи/суммы; отдельно продумать idempotency/429/503 и повторную доставку.
- `GET /api/public/stats`: рассмотреть короткий безопасный cache с учётом обновления статистики; без персональных данных.
- `/health`: решить, должен ли быть публичным, минимизировать раскрываемую информацию, оставить доступным проверкам деплоя.
- Не нарушать `/.well-known/acme-challenge/` и выдачу статических ассетов.

**Внедрять сначала в dry-run:** `limit_req_dry_run on;` и `limit_conn_dry_run on;` (проверить наличие директив в установленной версии Nginx), анализировать `$limit_req_status`, затем включать ограничение постепенно. Правила могут блокировать людей за одним NAT — тестировать реальные сценарии.

## Этап 2 — Fail2ban и вход в админку

- [ ] Проверить, установлен ли Fail2ban и как защищён SSH; настроить `sshd` jail с безопасными порогами и `ignoreip` для доверенного администрирования, если это обосновано.
- [ ] Для Nginx/API предусмотреть **отдельный** jail по достоверным access/error логам с устойчивым шаблоном; не банить всех за случайный 429.
- [ ] Логи без email/телефонов/токенов/платёжных реквизитов, настроить logrotate, права и срок хранения.
- [ ] Проверить, что Fail2ban не забанит IP доверенного CDN вместо пользователя. За прокси лучше применять решение на edge/WAF; UFW-bans по реальному IP при CDN могут оказаться бесполезны на origin.
- [ ] Рассмотреть двухфакторную аутентификацию админки и усиление приложения: IP-подмена, brute force, ограничение памяти счётчиков логина.

## Этап 3 — внешний анти-DDoS и защита origin

- [ ] Оценить защиту провайдера VDS и Cloudflare/альтернативный CDN+WAF с учётом доступности аудитории и необходимых сервисов.
- [ ] Подключить proxy/CDN для `artemcarbon.ru`, `www`, `api` **только после тестирования**: TLS end-to-end, `www` redirect, cookie/session, CORS, API POST, bank callback, DNS IPv6, Certbot.
- [ ] При Cloudflare: реальный IP принимать через `CF-Connecting-IP` **только от официальных доверенных диапазонов Cloudflare** с `set_real_ip_from`/ `real_ip_header`, поддерживать диапазоны актуальными. Никогда не доверять произвольному заголовку от прямого клиента.
- [ ] Для реальной защиты origin ограничить входящие HTTP(S) **до адресов CDN и явно необходимых доверенных источников**; сделать это поэтапно, сохранив emergency access, мониторинг и rollback.
- [ ] GitHub Actions SSH не должен терять доступ при закрытии origin. SSH-правила не затрагивать до проверки отдельного доступа через консоль VDS / VPN / фиксированный адрес; адреса GitHub-hosted runner могут меняться.
- [ ] Убедиться, что банк действительно может достичь `api.artemcarbon.ru` без JS challenge и не получает блокировки WAF. Для webhook применять адресное правило, не отключая проверку Token.
- [ ] Не предполагать, что смена DNS скрыла старый IP: он уже был публичным, а сетевой DDoS на этот IP возможен без фильтрации у провайдера.
- [ ] Перед firewall cutover проверить обновление сертификатов: proxy/allowlist не должны ломать HTTP-01 (либо перейти на подтверждённо работающий DNS-01).

## Рекомендуемые отдельные PR

1. **PR A — Nginx + deploy persistence:** zones, route-specific limits, dry-run, checks, rollback; без CDN/firewall. Именно этот PR должен обновить `scripts/deploy-full-vds.sh`, потому что он перезаписывает Nginx.
2. **PR B — Fail2ban + monitoring:** конфигурации, проверяемые логи, тесты; осторожно с CDN.
3. **PR C — внешняя защита и origin restriction:** после выбора CDN/провайдера, настройки DNS, TLS и доверенных IP; требуется доступ к панели DNS и провайдера, нельзя сделать только правкой GitHub.
4. **PR D — усиление API:** защита дорогих запросов, отдельная идемпотентность `POST /api/orders`, контроль ресурсов и bank callback.

## Критерии готовности

- [ ] Сайт/API/админка доступны; оплата и callback проходят без необоснованных 429/403.
- [ ] Повышенная активность даёт контролируемые 429, а не падение API/PostgreSQL.
- [ ] HTTPS и `certbot renew --dry-run` работают.
- [ ] Защита не исчезает после нового deploy.
- [ ] SSH и GitHub Actions работают; rollback проверен.
- [ ] У провайдера/внешнего сервиса подтверждена upstream-защита от сетевых DDoS; Nginx без неё не считается полной защитой.
