# PR #65 — Nginx anti-flood, первая безопасная стадия

**Статус:** реализовано в отдельной ветке, до слияния **не развёрнуто на VDS**. Первое включение — только наблюдение за превышением лимитов, **без блокировки** по частоте запросов или количеству соединений. Основано на плане [ANTI_DDOS_PLAN.md](./ANTI_DDOS_PLAN.md) из PR #64 (план пока ожидает merge).

## Защита и ограничения

| Маршрут | Nginx-лимит | Действие после deploy |
|---|---|---|
| `/api/` на `artemcarbon.ru` и `api.artemcarbon.ru` | 8 req/s/IP, burst 20; до 20 одновременных соединений/IP | **Dry-run**, мониторинг |
| `/api/admin/login` (оба домена) | 5 req/min/IP, burst 3; до 20 соединений/IP | **Dry-run**, мониторинг |
| `/api/payments/tbank/notification` | Нет Nginx rate/connection limit; signature verification остаётся в Node.js | Без блокировки банковских повторов |
| `/health` и статические файлы | Без лимитов | Не изменены |
| ACME, TLS, HTTP→HTTPS, `www` | Без лимитов | Не изменены |

Для маршрутов `/api/` включено `client_max_body_size 128k`; HTML/фото не ограничиваются этим лимитом. Проверять возможные легитимные большие тела до включения реальных платежей.

**Важно:** на этапе dry-run Nginx **не возвращает 429 из-за этих лимитов**. Код 429 настроен на будущий этап enforcement. Другие обработчики, в том числе лимит приложения на вход в админку, по-прежнему могут возвращать 429.

## Где конфигурация

- `config/nginx/artemcarbon-antiflood.conf`: зоны ограничений и безопасный формат access log (без query string, cookie или тела).
- `config/logrotate/artemcarbon-antiflood`: ежедневная ротация и хранение семи файлов логов.
- `scripts/deploy-full-vds.sh`: установка этих файлов в системные каталоги, маршруты Nginx, проверка `nginx -t`, откат конфигов при ошибке проверки или reload. Никаких изменений SSH/UFW/DNS.
- `tests/test_nginx_antiflood.py` и workflow CI: проверки на дублирование правил, отсутствие rate limit у банковского webhook и реальный `nginx -t` с временным тестовым сертификатом.

После merge автоматический deploy обновляет конфигурацию. **Обязательно проверить статус Actions и выполнить smoke**; отсутствие ошибки в CI не означает успешный production deploy.

## Проверки после первого деплоя

1. Сохранить выводы `sudo nginx -t`, `sudo ss -lntp` и `sudo systemctl status nginx --no-pager`.
2. Убедиться, что `https://artemcarbon.ru/`, `https://www.artemcarbon.ru/`, `https://artemcarbon.ru/admin/`, `https://api.artemcarbon.ru/health` и `/api/public/stats` доступны.
3. Проверить аутентификацию админки и форму выбора 1–10 / 10 / 25 / 50 / 100.
4. Изолированно проверить логи без нагрузки: `sudo tail -n 60 /var/log/nginx/artemcarbon-antiflood.log`. Поле `req_limit` показывает `PASSED`, `DELAYED_DRY_RUN` или `REJECTED_DRY_RUN`, а `conn_limit` — аналогично. Значения зависят от версии Nginx. Не публиковать реальные IP покупателей в чат.
5. Проверить статистику по `status`, `req_limit`, `conn_limit` и частоту легитимных превышений, особенно при мобильном NAT и в периоды пиковой активности.
6. Убедиться, что уведомления Т-Банка не блокируются; **не отправлять фиктивные банковские webhook на production**.
7. Повторить `sudo certbot renew --dry-run` и проверить GitHub Actions повторным безопасным деплоем.

## Переход к активному ограничению

Это отдельное решение после наблюдения и оценки ложных срабатываний. Нужно будет:
- выбрать пороги на основе логов;
- убрать `limit_req_dry_run on;` и `limit_conn_dry_run on;` только у выбранных маршрутов;
- применить ограничение поэтапно с мониторингом HTTP 429, 5xx и времени ответа;
- предусмотреть допустимый трафик с одного IP (NAT, мобильные сети, webhook);
- закрепить изменения в deploy-скрипте, протестировать и открыть отдельный PR.

## Откат

Скрипт развёртывания сохраняет предыдущие версии сайта Nginx, зоны и logrotate в защищённой временной директории на время изменения и восстанавливает их при ошибке `nginx -t` или reload. Если проблемы обнаружились **после успешного deploy**, нужно откатить коммит через отдельный PR либо вручную вернуть предыдущую версию конфигурации на VDS и проверить `nginx -t` до reload. Важное замечание: последующий deploy снова запишет конфигурацию из актуального `main` — поэтому ручное исправление без GitHub не является постоянным.

## Следующие стадии (в PR #65 не входят)

- Fail2ban для SSH / отдельных логов, защита от перебора.
- Мониторинг, алерты и определение допустимой нагрузки.
- CDN/WAF, доверенные диапазоны IP и защита от прямых подключений к origin.
- Дополнительная идемпотентность `POST /api/orders` и защита дорогостоящих платежных операций.

**Nginx не остановит сетевой DDoS, забивающий канал VDS.** Нужна upstream-защита провайдера или внешний сервис, который может фильтровать трафик до попадания на сервер.
