# План: внешний мониторинг Artem Carbon через Uptime Kuma на dvizh-school.ru

**Статус:** запланировано, **не установлено**. Этот документ фиксирует задачу для отдельного этапа после настройки, когда будет подтверждено состояние старого сервера. Изменения в репозитории не включают установку Docker-контейнеров или правки Nginx.

## Зачем нужен отдельный мониторинг

На боевом VDS `195.209.222.219` работает собственный мониторинг Artem Carbon через `artemcarbon-monitor.timer` (каждые пять минут): сервисы, ресурсные метрики, HTTP 429/5xx, бан SSH и SMTP-уведомления на `motostrelok@yandex.ru` (PR #71, #72). Тестовая почта доставлена; системный журнал показал регулярное успешное завершение без проблем.

**Ограничение:** при выключении боевого VDS, сбое канала связи или недоступности исходящего SMTP внутренний мониторинг не сможет уведомить. Внешний мониторинг должен выполняться **с независимого сервера**.

## Предлагаемая архитектура

- **Сервер мониторинга:** существующий `dvizh-school.ru` (hostname `driving-school-web`). Не использовать боевой Artem Carbon VDS для размещения Kuma.
- **ПО:** Uptime Kuma (self-hosted open-source), отдельный Docker-контейнер и постоянный Docker volume / bind mount для состояния.
- **Проверки:** `https://artemcarbon.ru/` (статическая главная) и `https://api.artemcarbon.ru/health` (Node API), тип HTTP(S), интервалы 60 секунд.
- **Условия оповещения:** предварительно 3 последовательные неудачные проверки и одно письмо при восстановлении; точные параметры выставить в панели после установки.
- **Email:** внешний сервис на `dvizh-school.ru` отправляет аварийные сообщения на `motostrelok@yandex.ru`. Использовать существующий проверенный SMTP Mail.ru с отдельными настройками, не выводить и не коммитить пароль.
- **Веб-интерфейс:** при согласовании отдельный поддомен `monitor.dvizh-school.ru` с HTTPS (Nginx reverse proxy), доступ по учётной записи администратора. Не публиковать порт контейнера наружу.
- **Хранение и восстановление:** данные Kuma в постоянном томе, периодические резервные копии конфигурации/БД Kuma, документированный способ восстановления.
- **Изоляция:** ограничить ресурсы контейнера (память/CPU), чтобы мониторинг не ухудшал работу сайта автошколы, LMS и БД.
- **Ограничение независимости:** оба сервера могут использовать один провайдер или сеть; при общем сетевом сбое внешний сервер тоже может не отправить уведомление. Для высокой надёжности пригодится третий независимый канал/провайдер.

## Этап 1 — безопасный аудит старого сервера (только чтение)

Перед установкой получить и оценить:

```bash
docker --version
docker compose version
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
free -h
df -h /
ss -lntp
sudo nginx -t
sudo ufw status verbose
```

Задачи: проверить ресурсы, свободный локальный TCP-порт, DNS-доступность планируемого поддомена, существующие контейнеры/виртуальные хосты, активные правила firewall и способ обновления Docker.

**Не резервировать заранее порт 3001:** на старом сервере там может работать LMS. Выбираем отдельный свободный порт на `127.0.0.1` по фактическому состоянию.

## Этап 2 — установка отдельным PR/ручным контролируемым запуском

1. Выбрать конкретную поддерживаемую версию/образ Uptime Kuma; зафиксировать версию или digest, не использовать `latest` в бесконтрольном production-развёртывании.
2. Подготовить отдельный `compose.yaml` с `restart: unless-stopped`, volume, ограничениями ресурса и портом **только на `127.0.0.1`**.
3. Установить контейнер, убедиться, что автозапуск автошколы, PostgreSQL и LMS не изменился.
4. Добавить отдельный Nginx server block для `monitor.dvizh-school.ru` **без перезаписи существующих конфигураций**; получить сертификат HTTPS через Certbot после проверки DNS.
5. Создать первого пользователя панели и надёжный пароль; закрыть публичное управление, запретить анонимный доступ и включить дополнительное ограничение доступа, если необходимо.
6. Создать два HTTP(S)-монитора, проверить коды ответов, TLS-проверку, тайм-ауты и уведомления.
7. Подключить SMTP на получателя `motostrelok@yandex.ru` и отправить тестовое сообщение из панели.
8. Настроить резервное копирование и проверку восстановления данных Kuma.
9. Зафиксировать фактические конфигурации и эксплуатационные команды **без секретов** в документации.

## Этап 3 — приёмочные проверки

- [ ] Оба URL имеют статус UP; история проверок накапливается.
- [ ] Таймер и веб-сервис Kuma переживают перезапуск контейнера/сервера.
- [ ] Письмо SMTP доставлено на `motostrelok@yandex.ru`.
- [ ] Проверка ошибочного тестового URL вызывает уведомление DOWN без остановки реального сайта.
- [ ] Исправление тестового URL вызывает ровно одно уведомление UP.
- [ ] Панель доступна только через HTTPS и требует авторизацию.
- [ ] Порт Kuma слушает только loopback и не открыт на публичном IP.
- [ ] Сервисы `dvizh-school.ru`, LMS и текущий Docker-стек не деградировали.
- [ ] В резервной копии доступны настройки мониторов; восстановление проверено.
- [ ] Документация обновлена фактическими путями, портами и процедурами отката.

**Нельзя тестировать DOWN путём остановки Nginx/Node/PostgreSQL боевого Artem Carbon**, нарушения DNS или изменения firewall. Нужен отдельный временный тестовый endpoint/монитор.

## Откат

Предварительно сохранить конфигурацию Nginx, состав контейнеров и текущее состояние UFW. При проблеме отключить только новый Nginx vhost и контейнер Kuma, проверить `nginx -t` и вернуть предыдущую конфигурацию. Не удалять Docker volumes и не выполнять массовую очистку Docker.

## Следующее действие

Когда вернёмся к задаче — начать с вывода аудита этапа 1, затем подготовить отдельный PR с `compose.yaml`, инструкциями и тестами. **Текущий PR — только фиксация архитектуры и плана; установка отложена по решению пользователя.**
