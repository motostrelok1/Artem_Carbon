# PR #71 — автоматический мониторинг Artem Carbon и Telegram

Проверка **каждые 5 минут** через systemd timer. Сервис ничего не изменяет в Nginx, SSH, UFW, Fail2ban, PostgreSQL или платежах: только читает состояние и отправляет уведомления.

## Что проверяется

| Сигнал | Порог | Оповещение |
|---|---|---|
| HTTPS сайт `https://artemcarbon.ru/` и API `https://api.artemcarbon.ru/health` | Недоступность на двух последовательных проверках | Проблема и восстановление |
| Сервисы `nginx`, `postgresql`, `artems-carbon`, `fail2ban`, `ssh` | Неактивны на двух проверках | Проблема и восстановление |
| Память `MemAvailable` | Использовано от **90%** на двух проверках | Проблема и восстановление |
| Корневой диск | Использовано от **85%** на двух проверках | Проблема и восстановление |
| HTTP **5xx** в журнале Nginx API | **5 и более** за последние 5 минут | Сразу при обнаружении и восстановление |
| HTTP **429** в журнале Nginx API | **20 и более** за последние 5 минут | Сразу при обнаружении и восстановление |
| Новые SSH-блокировки Fail2ban | **10 и более** с предыдущей проверки (обычно 5 минут) | Сразу при обнаружении и восстановление |

Метрики HTTP относятся к запросам, записанным в `/var/log/nginx/artemcarbon-antiflood.log`, то есть к API, а не к любым файлам сайта. Парсер смотрит временные метки с часовым поясом и исключает записи старше пяти минут; анализирует последние 15 000 строк текущего файла. После logrotate или при очень большом потоке статистика может быть неполной. Fail2ban учитывается по росту счётчика `Total banned`; при перезапуске счётчик может сброситься.

## Защита от спама

Повторных оповещений по одной и той же активной проблеме нет. Состояние инцидентов сохраняется атомарно в `/var/lib/artemcarbon-monitor/state.json` (только root), поэтому дедупликация переживает перезапуск скрипта. При нормализации приходит **одно** сообщение о восстановлении. Если Telegram не ответил, сообщение повторяется на следующей проверке. Уведомления не содержат IP посетителей, адреса покупателей, токенов или тело запросов.

## Деплой

После слияния PR #71 текущий production deploy:
1. Проверит синтаксис Python.
2. Установит скрипт как root-owned `/usr/local/libexec/artemcarbon-monitor/check.py`.
3. Установит `/etc/systemd/system/artemcarbon-monitor.service` и `.timer`.
4. Включит таймер на каждую пятую минуту (`OnCalendar=*:0/5`).
5. **Не создаст конфигурацию Telegram и не изменит существующий Fail2ban.**

До настройки Telegram мониторинг собирает данные и пишет агрегированные статусы в systemd journal, но **сообщения не отправляет**. Токены никогда не коммитить в GitHub.

Проверка после зелёного деплоя:

```bash
sudo systemctl is-active artemcarbon-monitor.timer
sudo systemctl list-timers --all artemcarbon-monitor.timer
sudo systemctl start artemcarbon-monitor.service
sudo journalctl -u artemcarbon-monitor.service -n 30 --no-pager
```

## Подключение Telegram

1. В Telegram создать бота через официального `@BotFather`, получить токен. Отправить боту личное сообщение `/start`. Для канала или группы добавить бота и дать право писать сообщения.
2. Получить `chat_id` адресата (числовой ID беседы или `@имя_публичного_канала`). **Не отправлять токен и chat_id в чат поддержки, логи или GitHub**.
3. На VDS создать root-only файл вручную:

```bash
sudo install -m 0600 -o root -g root /dev/null /etc/artemcarbon-monitor.env
sudo nano /etc/artemcarbon-monitor.env
```

Содержимое (подставить реальные значения):

```ini
ARTEM_MONITOR_BOT_TOKEN=123456:REPLACE_WITH_SECRET
ARTEM_MONITOR_CHAT_ID=123456789
```

Сохранить файл, затем проверить права и отправить **одно тестовое сообщение**, не выводя секреты:

```bash
sudo chmod 600 /etc/artemcarbon-monitor.env
sudo bash -c 'set -a; . /etc/artemcarbon-monitor.env; set +a; exec python3 /usr/local/libexec/artemcarbon-monitor/check.py --test-telegram'
```

Ожидаемый вывод: `Telegram test sent`; в Telegram должно прийти сообщение `Artem Carbon — тест мониторинга Telegram`. Таймер не требуется перезапускать: `EnvironmentFile` читается systemd при каждом запуске service.

Если тест не удался, проверить, что боту отправлено `/start`, chat ID верен и VDS может подключаться к `api.telegram.org:443`, **не публикуя токен**.

## Ограничения и откат

- При полном отключении VDS или его сетевого канала **внутренний таймер не сможет отправить уведомление**. Для этого понадобится независимый внешний uptime-монитор. Сайт может быть недоступен из определённого региона, но VDS видит HTTPS здоровым.
- Разовая краткая недоступность сайта/сервиса может не привести к уведомлению: для доступности предусмотрены 2 проверки подряд.
- Пороги зашиты константами в `scripts/monitoring/check.py` и меняются через отдельный PR с тестированием.
- Для временной остановки мониторинга:

```bash
sudo systemctl disable --now artemcarbon-monitor.timer
```

Это не отключает Nginx, Fail2ban или сайт. Для постоянного удаления нужны revert PR или отдельная правка deploy-скрипта; иначе следующий деплой снова активирует таймер.

Для удаления Telegram-доступа достаточно убрать root-only `/etc/artemcarbon-monitor.env` или отозвать токен через BotFather. **Не публиковать содержимое env в диагностическом выводе.**
