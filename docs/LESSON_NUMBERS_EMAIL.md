# ARTEMS CARBON: номера приобретённых видеоуроков и письмо

## Изменение
Каждый подтверждённый платеж `CONFIRMED` за видеоуроки получает столько **уникальных** номеров в диапазоне 0001..9500, сколько уроков куплено. Пример: 3 урока = 0147, 3821, 9076 (условный пример; реальные номера назначает PostgreSQL). Все номера одного заказа сохраняются в `lesson_number_pool` с `order_id`. По `orders.customer_id` и `customers.email` определяется покупатель, а ФИО и телефон остаются снимком в `orders`.

При повторном webhook `CONFIRMED` дополнительные номера **не назначаются**. Назначение проходит в одной транзакции с подтверждением заказа и постановкой письма в `email_outbox`. Глобальная блокировка PostgreSQL предотвращает одновременное назначение одного номера. `number` — PRIMARY KEY; письмо содержит только номера, прочитанные из БД. Изменение текста письма ничего не меняет в реестре.

**Важно:** номер не является криптографически неподделываемым сертификатом. При проверке действителен только реестр оплаченных заказов в БД; письма и скриншоты не служат источником истины. Администратор должен иметь проверку по БД и журнал аудита перед проведением выбора получателя.

При `REFUNDED` номера получают `voided_at` и больше не участвуют в активных подтверждённых покупках. Номера **не переназначаются**, сохраняется история. Частичные возвраты, отмена после выдачи и механизм выбора победителя не реализованы; требуются отдельная политика и тесты.

## Безопасное применение на VDS
1. Не включать реальные платежи, пока юридически не согласован механизм передачи автомобиля и влияние дополнительных покупок.
2. Применить `server/sql/004_lesson_numbers.sql` к **artems_carbon** до обновления API.
3. Проверить, что в `lesson_number_pool` есть ровно 9500 свободных номеров и 0 присвоенных; убедиться, что нет старых оплаченных заказов, которым требуются номера.
4. Обновить серверный код через `git pull --ff-only`, запустить `npm test`, только после этого `systemctl restart artems-carbon`.
5. Проверить тестовый `CONFIRMED`, повтор этого webhook, конкурирующие подтверждения, полный возврат, недостаток номеров и последующую доставку письма. Не использовать реальные деньги для этих тестов.
6. Перед реальной оплатой добавить резервирование лимита 9500 на стадии создания платежей: текущий webhook может обнаружить нехватку **уже после** списания. При исчерпании номеров транзакция откатится, а платёж потребует ручной сверки/возврата. Это блокер запуска.
7. В базе номера привязаны к заказу. Доступ к реестру только через защищённую админку, не через публичный endpoint. Не публиковать список покупателей и номеров в открытом API.
8. Исправить политику возвратов, частичные возвраты и регламент акта определения получателя автомобиля до включения боевого терминала.

## Проверка
- `SELECT COUNT(*) FROM lesson_number_pool` = 9500.
- `SELECT number,order_id,voided_at FROM lesson_number_pool WHERE order_id IS NOT NULL ORDER BY assigned_at DESC LIMIT 10` — проверка реестра (на сервере, не в браузере).
- Письмо по видеоуроку **не отправляется** при отсутствии назначенных номеров; обработчик повторяет позднее.
