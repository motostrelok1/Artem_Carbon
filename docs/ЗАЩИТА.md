# ЗАЩИТА — план безопасности ARTEMS CARBON

Статус: **план работ, не доказательство устранения уязвимостей**. До завершения обязательных пунктов не включать боевые платежи. Этот документ фиксирует договорённости по безопасности сайта, API, админки, PostgreSQL, почты и данных покупателей.

## Что уже проверено по коду

- В серверной обработке заказа для полей покупателя применяются параметризованные запросы `pg` (`$1`, `$2` и т. д.). Это защищает **данный путь** от классического внедрения SQL через значения параметров. Полный аудит всех SQL-путей не проводился.
- Для покупки видеоурока `validateCourseBuyer` повторно проверяет на сервере ФИО, телефон, email, Instagram; проверка только браузером не считается защитой. Имя/отчество/фамилия ограничены символами и длиной, телефон нормализуется к `+7...`, Instagram проверяется по разрешённым символам.
- Шаблон письма экранирует HTML при подстановке части данных; это **не означает**, что XSS исключён на сайте и в админке.
- В API для заказов включена проверка `Origin`, но она **не заменяет** аутентификацию, защиту от ботов и rate limiting: прямой HTTP-клиент способен задавать заголовок `Origin`.
- Пароли SMTP и Т-Банка должны храниться только на сервере, а не в GitHub или браузере.
- `PAYMENTS_ENABLED=false` сохраняется до выполнения обязательных задач и интеграционного тестирования.

## P0 — обязательно до включения реальных платежей

- [ ] **Валидация email и заголовки письма.** Уточнить строгие ограничения длины, разрешённых форматов, нормализацию; явно отклонять CR/LF, управляющие и скрытые Unicode-символы в адресах и полях, используемых в почтовых заголовках. Проверять адрес до передачи в Nodemailer. При этом не удалять без необходимости допустимые адреса международных пользователей: документировать поддерживаемую политику.
- [ ] **Проверка всех полей заказа на сервере.** Проводить валидацию всех SKU и структур JSON (типы, размеры, количество, неизвестные ключи), не доверять клиентскому расчёту цены, повторно проверять значения на API. Физические товары и видеоуроки проверить раздельно.
- [ ] **Rate limiting и устойчивость API.** Ограничить частоту создания заказов, ошибок валидации, обращения к авторизации администратора, публичной статистике и чувствительным маршрутам. Учесть доверенный прокси/Nginx и реальный IP, ограничения по размеру/времени запроса, защиту от чрезмерного числа неоплаченных заказов и расходования ресурсов Т-Банка. Лимиты должны быть проверяемыми и не блокировать обычных покупателей.
- [ ] **Защита от ботов.** Рассмотреть Cloudflare Turnstile либо эквивалент с обязательной **серверной** проверкой токена и отказом при недействительной/повторной проверке. Не считать невидимый клиентский виджет достаточной защитой.
- [ ] **XSS и безопасный вывод.** Проверить все места вывода пользовательских данных на сайте, в админке и HTML-письмах; использовать `textContent`/контекстное экранирование, избегать `innerHTML` для пользовательских строк, URL строить из разрешённых схем. Внедрить и протестировать Content Security Policy для GitHub Pages и будущего домена.
- [ ] **Админка и авторизация.** Убрать зависимость от демонстрационного пароля как защиты реальных данных. Использовать только серверную авторизацию; защитить от CSRF, ограничить попытки входа, проверить cookie `Secure/HttpOnly/SameSite`, CORS, выход, истечение сессии и доступ без авторизации. Проверить конфигурацию при размещении фронтенда на GitHub Pages и API на отдельном домене.
- [ ] **Секреты и БД.** Проверить права `.env`, системного пользователя `artems-api`, разрешения PostgreSQL по принципу минимальных привилегий; исключить публикацию паролей и ключей в логах, ошибках и Git. Защитить резервные копии, проверить восстановление, ограничить доступ к реестру покупателей и номеров.
- [ ] **Платежи и номера.** Сверить подписанный webhook Т-Банка, `TerminalKey`, `PaymentId`, сумму, статус, идемпотентность и возвраты; запретить выдачу номеров до подтверждения платежа. Исправить гонки при продаже последних номеров 9500: резервирование, лимит и порядок возврата при ошибках. Протестировать повторные и параллельные уведомления и частичные возвраты.
- [ ] **Персональные данные и юридические документы.** Подготовить и опубликовать политику обработки персональных данных, обязательные уведомления/согласия по применимому законодательству, сроки хранения и удаления, порядок доступа/исправления, защиту резервных копий. Отдельно согласовать правовой механизм передачи автомобиля и правила выбора получателя.
- [ ] **HTTPS/L7.** Проверить TLS, заголовки безопасности, reverse proxy, ограничения по запросам и план размещения под L7-защитой (Selectel либо другой провайдер). L7 не заменяет безопасность кода.

## P1 — усиление надёжности и контроля

- [ ] Записывать структурированные события безопасности (отказы проверки, блокировки rate limit, ошибки webhook и авторизации) без ФИО, телефонов, email, токенов, секретов и полных тел запросов; настроить мониторинг и оповещения.
- [ ] Для номеров видеоуроков добавить независимый проверочный код/токен и защищённую проверку подлинности без раскрытия ФИО и телефона. Сама четырёхзначная последовательность не является секретом.
- [ ] Добавить неизменяемый или защищённый от подмены аудит назначения/аннулирования номеров и административных изменений. Описать процедуру контрольной сверки до выбора получателя автомобиля.
- [ ] Проверить безопасность файлов, HTML-писем и встроенной картинки `5.jpg`/`5.jpeg` (фиксированная локальная вложенная фотография, не произвольный путь из запроса).
- [ ] Проверить повторную отправку писем, ограничения почтового провайдера и восстановление после падения обработчика без выдачи новых номеров.
- [ ] Регулярно запускать `npm audit --omit=dev`, следить за зависимостями, обновлениями безопасности, `node --check` и тестами CI.

## Автоматические проверки — критерии приёмки

### SMOKE / критичные
- [ ] SQL-подобные строки в любом пользовательском поле не изменяют структуру запросов и БД.
- [ ] HTML/JS-пейлоады в полях не исполняются ни на сайте, ни в админке, ни при просмотре писем.
- [ ] CRLF и управляющие символы в email не попадают в SMTP-заголовки.
- [ ] Без обязательных полей или с неверными типами/форматами API возвращает 4xx; запись заказа и платёж не создаются.
- [ ] Прямой HTTP-запрос в обход формы проходит те же серверные ограничения.
- [ ] Неавторизованный запрос к админским заказам/персональным данным возвращает 401/403.
- [ ] Повторные webhook подтверждения не создают дубликаты номеров и писем.
- [ ] Одновременные покупки у предела 9500 не превышают лимит и не списывают деньги без управляемого сценария выдачи/возврата.
- [ ] Поддельный webhook и несовпадение суммы/PaymentId отклоняются.
- [ ] Секреты и персональные данные не возвращаются в ответах об ошибках и не попадают в публичные логи.

### Дополнительные
- [ ] Граничные длины, пробелы, Unicode, дефисы, апострофы, нестандартные номера телефона.
- [ ] JSON-массивы/объекты вместо строк, вложенные массивы, неизвестные SKU, очень большие числа.
- [ ] Rate limit при серии запросов и восстановление после окна блокировки.
- [ ] Содержимое и заголовки CSP/CORS/Cookie на Pages и реальном API.
- [ ] Отправка и повторная отправка писем при временной недоступности SMTP.
- [ ] Ротация SMTP/банковских секретов, права службы, резервное копирование и тест восстановления.

## Порядок реализации
1. Базовые серверные проверки ввода, email, защита HTML и тесты на инъекции.
2. Rate limiting, антибот и ограничения ресурсов.
3. Админка, сессии, CSP/CORS/CSRF, секреты и права БД.
4. Проверка сценариев оплаты, лимита 9500, возвратов, реестра номеров.
5. Интеграционный security-smoke на тестовом терминале и отдельной БД.
6. Проверка юридических документов и инфраструктуры L7/HTTPS.
7. Только после успешной проверки и разрешения владельца — отдельное решение о включении боевых платежей.

### Примечание
Зелёные CI-тесты не доказывают отсутствие всех уязвимостей. Для каждого пункта следует приложить код, проверку и отчёт о результатах; документацию и тесты поддерживать в одном PR либо связанных PR. На данном этапе этот PR **только фиксирует объём и критерии защиты**, не включает новый режим платежей и не претендует на исправление всех рисков.
