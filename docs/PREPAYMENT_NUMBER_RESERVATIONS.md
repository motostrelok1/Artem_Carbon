# PR #75 — резервирование номеров ДО открытия оплаты

**Статус:** код для изолированного тестирования; **не готов к включению реальных платежей**. Ветка не должна активировать `PAYMENTS_ENABLED` или менять платёжные ключи. Это промежуточный этап безопасности.

## Проблема старой схемы

Раньше `/api/orders` создавал заказ, затем сразу выдавал `PaymentURL`. Номера 0001–9500 выделялись только после банковского `CONFIRMED`. Если свободных номеров было недостаточно, покупатель уже мог внести деньги.

## Новая схема

1. До обращения к банку `POST /api/orders` создаёт заказ в PostgreSQL.
2. В **той же транзакции** для видеоурока через `reserveLessonNumbers` резервируется ровно `quantity` номеров. Общая PostgreSQL advisory transaction lock сериализует выдачу между конкурентными покупателями. Уже проданные, возвращённые и зарезервированные номера **не доступны** для новых заказов.
3. Если свободных номеров не хватает, транзакция откатывается, API отвечает **HTTP 409** (`Insufficient available lesson numbers`). **Банковский /Init при этом не вызывается**.
4. Только после успешного COMMIT вызывается `/v2/Init`, покупатель получает `PaymentURL`.
5. При подписанном `CONFIRMED` фиксируются **те же самые зарезервированные номера**; новые номера после списания денег НЕ выделяются. После фиксации резервирование очищается, номера переходят в постоянную запись, письмо ставится в `email_outbox`.
6. При повторном `CONFIRMED` номера повторно не назначаются. При `REFUNDED` номера помечаются void, не переиспользуются.

## Особый риск: сроки брони и банк

`reservation_expires_at` устанавливается на 30 минут **только как момент для последующей сверки**. Сам по себе дедлайн **не освобождает** номера, поскольку платёж от банка может прийти позже. После неясной ошибки /Init бронь тоже не освобождается автоматически: неизвестно, успел ли банк зарегистрировать платёж.

Для production нужны дополнительные механизмы:

- Фоновая сверка старых `pending` с Т-Банком через GetState и подтверждение терминального/отменённого статуса **до освобождения** резерва.
- Отдельная фиксация статуса разрезервирования в БД с audit trail, защита гонок с `CONFIRMED`, идемпотентность.
- Явная компенсация или процедура возврата, если банковская оплата всё же прошла после подтверждённого освобождения. Без сверки гарантировать отсутствие оплаты за уже переиспользованный номер нельзя.
- Рассмотреть двухстадийную схему банка (авторизация и подтверждение) **только после проверки настроек терминала и требований фискализации**, чтобы можно было не списывать деньги при нехватке ресурса.
- TTL и массовые незакрытые заказы могут временно занять весь пул; использовать неограниченное автоматическое освобождение нельзя.

Поэтому даже после этой миграции **НЕ включать реальные продажи без банковской сверки, тестов возвратов и юридической проверки**.

## Миграция

Новый файл: `server/sql/006_pre_payment_reservations.sql`; добавляет поля `reserved_order_id`, `reserved_at`, `reservation_expires_at`, индексы и GRANT. Исторические записи `lesson_number_pool` не удаляет, выделенные номера не меняет.

Порядок: сначала применить миграцию в **изолированной тестовой PostgreSQL** и запустить интеграционные тесты через `TEST_DATABASE_URL`; затем после утверждения стратегии релиза — миграцию отдельно на VDS, с резервной копией и контролем отсутствия работы с платежами. Только затем выкатывать код, если платежи не выключены. **Обычный deploy-скрипт не применяет миграции автоматически.**

Поскольку `PAYMENTS_ENABLED=false` должен оставаться установленным, слияние новой версии приложения не означает включения продаж.

## Проверки

- Создание одного заказа резервирует нужное количество номеров.
- `CONFIRMED` использует те же номера, снимает метку резервирования; повторный webhook идемпотентен.
- Два одновременных заказа не получают одинаковые номера.
- При исчерпании всех 9500 запись заказа откатывается с HTTP 409, банк не вызывается.
- `REFUNDED` не освобождает однажды присвоенные номера для повторной выдачи.
- Продукция, отличная от видеоуроков, не занимает номера.
- Тестовые платежи работают только с локальным mock T-Банк в GitHub Actions и изолированной БД.
- Не тестировать реальные списания, не выдавать серийные номера вручную.
