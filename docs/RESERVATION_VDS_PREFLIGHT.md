# Проверка VDS перед миграциями 006–007 (без изменений production)

**Назначение:** перед развёртыванием механизма резервирования (PR #75) и сверки с банком (PR #76) собрать безопасные сведения о текущем Artem Carbon VDS. **Эти команды не применяют миграции, не включают платежи и не трогают данные.**

## Предварительные условия

- Ветка PR #75 с миграциями 006 и 007 должна пройти CI; **развёртывание только после одобрения совместимости**.
- Нужен терминал на новом VDS `195.209.222.219`.
- Не передавать в чат `.env` целиком, `DATABASE_URL`, банковские ключи, SMTP-пароли и IP покупателей.
- Не запускать с боевой базой `npm test`, если в окружении указан production `TEST_DATABASE_URL`: интеграционный тест применяет SQL и пишет заказы. CI использует отдельную `artems_carbon_ci`.

## 1. Проверка файлов и конфигурации (без секретов)

После появления скриптов на сервере (их можно загрузить отдельно, **не используя production deploy до миграций**) запустить:

```bash
sudo bash /path/to/preflight-vds-config.sh /opt/artems-carbon/server/.env
```

Скрипт печатает лишь наличие переменных, значение `PAYMENTS_ENABLED`, флаг `RECONCILIATION_ENABLED` и активность служб PostgreSQL/Nginx/Node. Пароли не раскрываются.

**Условие допуска к дальнейшим действиям:** `PAYMENTS_ENABLED=false` и `RECONCILIATION_ENABLED` не равен `true`. Если настройки иные — **остановиться**, ничего не изменять автоматически.

Примечание: отсутствие настроек магазина `SMTP_*` на новом VDS уже было выявлено раньше; Email для **системного мониторинга** живёт в отдельном root-only `/etc/artemcarbon-monitor.env`. Эти настройки разные.

## 2. Проверка существующей базы (только SELECT)

Если скрипт загружен на VDS:

```bash
sudo -u postgres bash /path/to/preflight-reservations.sh artems_carbon
```

Он принудительно включает `default_transaction_read_only=on` и выводит только агрегаты:

- Имя БД, пользователя и read-only статус.
- Наличие `orders`, `order_items`, `lesson_number_pool`, `lesson_reservation_release_audit`.
- Список ожидаемых колонок (в том числе будущих `reserved_*`).
- Количество заказов `pending` и `paid`, число заказов без `PaymentId`.
- Размер пула номеров (ожидается 9500), сколько было назначено, помечено void, сколько пока не назначено.
- Количество некорректных номеров, потерянных внешних ключей и дублей PaymentId.

Внимание: `unassigned_old_schema` означает только `order_id IS NULL` и **после миграции 006 не учитывает незакреплённые брони**. Не интерпретировать этот показатель как доступные для продаж номера после включения резервирования.

При ошибках, неожиданном количестве 9500, существующих платежах или расхождении схем **не применять миграции до анализа**.

## 3. Тест миграций в GitHub Actions

CI `server-checks.yml` разворачивает отдельный PostgreSQL 16. Интеграционный тест накатывает миграции 001–007, повторно применяет 006/007 и проверяет необходимые столбцы и таблицу аудита. Это проверяет идемпотентность **структурных SQL**, но не заменяет проверку production-данных.

## 4. Следующий этап — отдельное контролируемое внедрение

1. Снять резервную копию целевой базы PostgreSQL, сохранить вне этой машины и проверить возможность восстановления.
2. Подтвердить фактический `PAYMENTS_ENABLED=false`, отсутствие активных продаж и исходную схему.
3. На отдельно восстановленной копии БД применить 006 и 007 и проверить целостность; не использовать реальную БД как тестовую.
4. После явного допуска применить миграции на VDS **в правильном порядке**, с `ON_ERROR_STOP`, проверить схему и перезапуск API.
5. Проверить внешние HTTPS /health, админку, регистрацию заказа при выключенном `PAYMENTS_ENABLED`, логи Node/Postgres/Nginx и мониторинг.
6. Не запускать сверку броней автоматически: worker разрешается только вручную с `RECONCILIATION_ENABLED=true` для подготовленного окружения.
7. Не включать реальные продажи до проверки тестового терминала Т-Банка, безопасной процедуры закрытия заказов без PaymentId, возвратов, фискализации и юридических условий.

## Риски и откат

Миграции 006–007 аддитивные и не должны удалять заказы, но в production возможны долгие блокировки DDL, данные старой версии и расхождения владельцев/прав. Полный откат после реальных продаж не может означать «удалить новые поля и заново продать номера»; сначала нужен разбор всех открытых резервов и банковских состояний. Никаких автоматических `DROP`/очистки на production.

**Этот PR — подготовка и тесты. Изменения VDS отсутствуют.**
