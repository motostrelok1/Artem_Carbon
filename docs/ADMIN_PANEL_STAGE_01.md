# Этап 01 — рабочая административная панель ARTEMS CARBON

Статус: реализация начата в `feat/admin-live-vds`. Документ описывает границы этапа и критерии приёмки. Наличие кода в ветке не означает, что этап развёрнут или принят.

## Цель

Заменить демонстрационную админку на защищённую панель, которая читает реальные данные из PostgreSQL ARTEMS CARBON. На этом этапе панель работает в режиме просмотра; изменение платежей, заказов, номеров и цен через интерфейс запрещено.

## Архитектурное решение

- Backend: существующий Node.js API и PostgreSQL на VDS.
- Админка: статические HTML/CSS/JS-файлы, отдаваемые с того же origin, что и API (путь `/admin/`). Это исключает зависимость авторизации от third-party cookies GitHub Pages.
- Все административные API защищаются серверной сессией; cookie: HttpOnly, Secure, SameSite=Strict, ограниченный срок действия.
- Пароль администратора и SESSION_SECRET хранятся только в приватном окружении VDS. Пароль проверяется по scrypt-хешу.
- Все ответы с персональными данными: `Cache-Control: no-store`.
- Секреты банка, SMTP и БД не возвращаются браузеру.
- Публичный GitHub Pages не должен содержать рабочую админскую авторизацию или доступ к персональным данным.
- Платежи остаются выключенными: `PAYMENTS_ENABLED=false`.

## Функциональные разделы

### 1. Вход и сессия
- Вход по паролю администратора.
- Серверная проверка пароля.
- Проверка текущей сессии при загрузке страницы.
- Выход с отзывом cookie.
- Ошибки входа и временное ограничение перебора.
- При отсутствии обязательной конфигурации — отказ в доступе, не demo fallback.

### 2. Обзор
- Оплаченные заказы.
- Уникальные покупатели с оплаченными заказами.
- Выручка по оплаченным заказам.
- Ожидающие и возвращённые заказы.
- Количество проданных видеоуроков из представления `public_lesson_sales`.
- Количество писем в очереди/ошибке.
- При пустой базе показывать достоверные нули; при ошибке API показывать ошибку, не подменять её нулями.

### 3. Аналитика
- Периоды: 24 часа, 7 дней, 30 дней, всё время.
- Число покупателей, оплаченных заказов, уроков и сумма продаж.
- Выручка по дням.
- Последние оплаченные позиции.
- В расчёт включаются только `paid`; возвращённые заказы не считаются продажами.
- Суммы передаются в копейках и форматируются в рубли на клиенте.

### 4. Заказы и покупатели
- Постраничный список (30 записей).
- Фильтр по статусу.
- Дата, сумма, статус, товары и количество.
- ФИО, телефон, email, Instagram.
- Идентификатор заказа и PaymentId.
- Присвоенные активные номера.
- Дата и версия каждого согласия.
- Данные доступны только после серверной авторизации.

### 5. Каталог
- Получение SKU, названия и серверной цены.
- Только просмотр на этапе 01. Редактирование цены не входит в этот этап.

### 6. Письма
- Состояния очереди: queued, sending, sent, failed, cancelled.
- Количество попыток, дата создания, следующей попытки и отправки.
- Фильтрация/постраничность при необходимости.
- Не показывать SMTP-пароль и содержимое секретных переменных.

### 7. Состояние системы
- Платежи включены/выключены.
- Наличие банковской конфигурации без раскрытия ключей.
- Состояние SMTP без раскрытия реквизитов.
- Наличие API и фискальных параметров.
- Настройки на этом этапе только для просмотра; изменение ENV из браузера запрещено.

## Безопасность и ограничения

- Никакого пароля 666666 и клиентской проверки пароля.
- Никаких фиктивных данных и демонстрационных счётчиков.
- Параметризованные SQL-запросы.
- Строгая проверка query-параметров и пагинации.
- Не включать персональные данные в логи.
- Не кэшировать ответы с заказами/покупателями.
- Сессия — HttpOnly Secure cookie, SameSite=Strict; UI и API должны иметь один origin.
- Для операций изменения данных в будущем потребуется отдельная CSRF-проверка и журнал аудита. На этапе 01 все API только GET, кроме входа/выхода.
- Не менять `PAYMENTS_ENABLED`, банковские реквизиты, SMTP и схему реальных платежей.

## Критерии приёмки

1. Без сессии все административные GET возвращают 401.
2. Неверный пароль не создаёт сессию; после лимита попыток возвращается 429.
3. Верный пароль создаёт HttpOnly Secure cookie; перезагрузка страницы сохраняет вход.
4. Выход отзывает cookie; повторный запрос возвращает 401.
5. Ни один секрет не присутствует в HTML/JS или JSON API.
6. Обзор, аналитика, заказы, каталог, письма и состояние системы получают данные из PostgreSQL/ENV.
7. Все пользовательские поля выводятся через textContent/экранированный рендер, не через innerHTML.
8. Фильтр и пагинация проверяются сервером.
9. Ошибка БД/API показывается как ошибка, не как нулевые показатели.
10. На телефоне панель остаётся пригодной для использования.
11. `npm test` и новый набор тестов административных маршрутов проходят.
12. `PAYMENTS_ENABLED=false` остаётся неизменным.
