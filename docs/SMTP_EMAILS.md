# Автоматические письма после подтверждённой оплаты (SMTP)

**Состояние: подготовлено, но EMAIL_ENABLED=false по умолчанию.** Пароль, сервер и поставщик почты заказчика ещё не предоставлены. Письма не отправляются из GitHub Pages; отправитель — серверный worker.

## Как работает

1. Т-Банк отправляет подписанное HTTP-уведомление о статусе `CONFIRMED`.
2. Сервер в **одной транзакции** помечает заказ как оплаченный и вставляет строку `email_outbox(order_id,'order_confirmation')`. Уникальный индекс не допускает второй записи для того же заказа.
3. Отдельный процесс `mail-worker.js` выбирает готовые письма из БД с `FOR UPDATE SKIP LOCKED`, помечает в `sending`, отправляет их через TLS SMTP и записывает `sent`. При ошибке — `failed` и задержка перед повтором (до 8 попыток).
4. Если заказ успел стать возвращённым до отправки, письмо отменяется.
5. Администратор видит статусы через защищённый `GET /api/admin/email-status`; в UI раздел «Письма».

В письме: номер заказа, состав покупки, количество, сумма, контакт Артёма. **Ссылка на закрытый видеоурок пока не включена**, потому что индивидуальная авторизованная выдача доступа ещё не реализована; отправлять общую публичную ссылку небезопасно. Кассовый чек выдаёт касса/провайдер фискализации отдельно.

## Настройка на VDS / Selectel

1. Создать отдельный почтовый ящик, например `orders@домен-заказчика.ru`.
2. Уточнить у провайдера адрес SMTP-сервера, порт и способ авторизации. Для Яндекс 360 и Mail.ru часто используются порт **465** и пароль приложения, но конкретные параметры проверить в кабинете провайдера.
3. Проверить и настроить DNS SPF, DKIM, DMARC для домена отправителя.
4. Применить миграцию: `psql -v ON_ERROR_STOP=1 -f sql/002_email_outbox.sql` (после `001_sales.sql`).
5. В приватном окружении на сервере указать `EMAIL_ENABLED=true`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`. Не публиковать значения в GitHub и не отправлять пароли в чат.
6. Установить зависимости: `cd server && npm install && npm test`.
7. Проверить транспорт **без отправки письма**: `npm run mail:verify`.
8. Отправка одной доступной записи очереди: `npm run mail:once`. Настроить запуск отдельного процесса, например cron раз в минуту или systemd timer; запускать только с приватным окружением и после тестовой оплаты. Повторный запуск не должен обходить уникальность outbox.
9. Для SMTP-провайдеров уточнить суточные/часовые лимиты писем. При росте заказов — перейти на транзакционного провайдера без изменения принципа очереди.

## Ограничения и проверки

- Защита от двойной **постановки в очередь** есть, но SMTP-письма в редком случае могут доставиться повторно, если процесс упал после SMTP-ответа и до отметки `sent`. Стабильный Message-ID помогает почтовым клиентам, но не гарантирует exactly-once.
- Фактическую доставку в папку «Входящие» SMTP-ответ не гарантирует. SPF/DKIM/DMARC и наблюдение за bounce важны.
- Для реальных платежей проверить тестовые случаи CONFIRMED, повторное уведомление, REFUNDED, ошибка SMTP, восстановление после сбоя.
- Требуется политика хранения email по персональным данным, а также возможность исправления адреса администратором после проверки личности покупателя.
- Админка на GitHub Pages с `666666` — **демо**, для реальной работы нужна серверная аутентификация, подготовленная в PR по эквайрингу.
